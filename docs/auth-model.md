# 인증·권한 모델

Bidar가 사용하는 역할 계층과 권한 경계, 토큰 규칙, 비밀번호 규칙, 로그인 제한을 설명하는 문서입니다.

## 역할 계층

역할은 `user < moderator < admin < super_admin` 순서의 단일 계층으로 정의되어 있습니다(`src/core/roles.py`). 상위 역할은 하위 역할이 요구하는 모든 권한을 자동으로 만족합니다.

`User.is_superuser` 컬럼은 하위 호환을 위해 남아 있는 파생값입니다. 서버는 사용자를 생성하거나 수정하는 시점마다 이 값을 다시 계산하며, `role`이 `super_admin`일 때만 참이 되도록 유지합니다. 클라이언트가 보낸 `is_superuser` 값은 무시됩니다.

## 권한 경계

- `admin`은 사용자 조회와 활성화, 비활성화를 수행할 수 있습니다. 다만 대상 계정의 역할이 `admin` 이상이면 거절됩니다. admin이 자신과 동급이거나 상위인 계정을 건드려서 권한을 탈취하는 경로를 막기 위한 조치입니다.
- 사용자 생성과 역할 변경, 삭제는 `super_admin`만 수행할 수 있습니다.
- 활성 상태인 마지막 `super_admin` 계정은 강등하거나 비활성화하거나 삭제할 수 없습니다. 이 검사는 트랜잭션 안에서 활성 super_admin 행을 id 순으로 잠근 뒤에 수행합니다. 따라서 서로 다른 super_admin 두 명을 동시에 강등하는 요청이 겹쳐도 시스템에 super_admin이 전혀 남지 않는 상황은 발생하지 않습니다.
- 자기 자신을 삭제하거나 비활성화하는 요청은 대상이 몇 명이든 상관없이 항상 거절됩니다. 운영자가 스스로를 잠그는 사고를 막기 위한 조치입니다.

## 토큰 규칙

access 토큰과 refresh 토큰은 모두 `type` claim으로 구분되며, 서로 다른 용도로는 절대 통용되지 않습니다. 예를 들어 refresh 토큰을 `/auth/me`의 Bearer 토큰으로 사용하면 401이 반환됩니다.

`iat`와 `exp`는 항상 UTC 기준의 시간대 인식(aware) 값으로 발급됩니다. `sub`와 `user_id`, `type`, `exp`는 모든 토큰이 반드시 가져야 하는 필수 claim이며, 이 가운데 하나라도 없으면 검증 단계에서 거절됩니다.

RBAC 검증(`POST /rbac/verify-permission`과 `require_role` 의존성)은 토큰에 담긴 역할 claim을 신뢰하지 않습니다. 매 요청마다 데이터베이스에서 사용자의 현재 역할과 활성 상태를 다시 조회합니다. 따라서 계정이 강등되거나 비활성화되면 이미 발급된 access 토큰이라도 즉시 권한을 잃습니다.

refresh 토큰의 회전(rotation)과 서버 측 폐기 저장소는 아직 구현되어 있지 않으며, 후속 과제로 남아 있습니다(코드 내 `TODO(follow-up)` 주석을 참고하십시오).

## 비밀번호 규칙

비밀번호는 bcrypt로 해시하여 저장합니다. 최소 12자 이상이어야 하고, UTF-8로 인코딩했을 때 72바이트를 넘으면 안 됩니다.

bcrypt 자체는 72바이트를 넘는 입력을 자동으로 잘라냅니다. 그렇게 되면 72바이트까지 같은 두 비밀번호가 실질적으로 동일하게 취급됩니다. Bidar는 이를 서버에서 조용히 자르는 대신 입력 단계에서 명시적으로 거절합니다.

## 로그인 제한

`POST /auth/token`에는 IP당 분당 요청 제한이 적용되며, 기본값은 10회입니다. 이 제한은 워커 프로세스 내부 메모리를 사용하므로 워커마다 별도로 집계되고 재시작하면 초기화됩니다. 따라서 엄격한 쿼터가 아니라 완화 수단으로만 취급해야 합니다.

제한의 키는 `FORWARDED_ALLOW_IPS`를 거쳐 계산된 클라이언트 주소입니다. 이 설정값은 [환경 변수 문서](configuration.md)에서 설명합니다.
